# Architecture

This page shows how the library is put together: which module does what, and what happens between
a call like `playsets.findAll(search)` and the rows coming back from PostgreSQL.

## One idea: the SQL is already written

The library does **not** build SQL. Every statement of an entity (the `SELECT`, the `INSERT`, the
`UPDATE`) is a string constant generated by [stratastax-codegen](code-generation.md) (or written by
hand). The library's job is everything around those strings:

- running them, inside the right transaction, and binding their parameters;
- reading the rows that come back;
- adding the request-dependent part of a search: filter, sort, cursor and limit;
- explaining a write that matched nothing: was the row gone, or was the version stale?

[Why literal SQL](sql-first-design.md) explains why it was split this way.

## Modules

```
persistence-core       the API services use; no framework
   ▲        ▲
   │        └── persistence-csv       reads CSV files with the same row mappers
   │
persistence-reactive   runs the SQL with Vert.x, through a dialect
   ▲
   └── persistence-postgres   the PostgreSQL dialect (others can live in their own repository)

persistence-observability   every statement as an OpenTelemetry span under its request (on core)

persistence-test       test kit: assert on the SQL that ran (test scope only)
   ▲
   └── persistence-postgres-test   a PostgreSQL test database and its plan analyzer
```

| Module                      | You use it for                                                                                                                                                       |
|-----------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `persistence-core`          | The contracts a service depends on: `ReadAccess`, `CreateAccess`, `UpdateAccess`, `DeleteAccess`, `UnitOfWork`, `BatchResult` and the exceptions. No database code.  |
| `persistence-reactive`      | Running statements, transactions, rendering searches, and the helpers generated write code uses. Database-neutral: the SQL syntax comes from a `PersistenceDialect`. |
| `persistence-postgres`      | `PostgresDialect`, the PostgreSQL dialect the application wires into the executors and generated code puts in each `SearchSql`.                                      |
| `persistence-csv`           | Importing CSV files.                                                                                                                                                 |
| `persistence-observability` | Tracing every statement in production, under the request that caused it; see [observability.md](observability.md).                                                   |
| `persistence-test`          | Asserting on the SQL persistence code runs, independent of the database.                                                                                             |
| `persistence-postgres-test` | Running those tests against a real PostgreSQL, with query plans.                                                                                                     |

A service only needs `persistence-core`. The application's wiring and the generated access classes
are the only code that touches `persistence-reactive` and `persistence-postgres`. That keeps services free of driver details,
and makes them easy to test with a fake `ReadAccess`.

## Three packages per module
Every module splits its code the same way, so you can tell from an import what kind of thing it is:

| Package    | Meant for                                                                 | Examples                                                                 |
|------------|---------------------------------------------------------------------------|--------------------------------------------------------------------------|
| `api`      | code that **uses** the library                                            | `ReadAccess`, `UnitOfWork`, `VertxTransactionalExecutor`, `CsvRowReader` |
| `spi`      | code that **implements or extends** it: generated code, mappers, dialects | `QueryExecutor`, `RowMapper`, `SearchSql`, `PersistenceDialect`, `SearchSyntax` |
| `internal` | the module itself; invisible outside it                                   | `SearchSqlWriter`, `VertxRowContext`                                     |

The modules are compiled in Kotlin's explicit API mode, so nothing becomes public by accident. The
public API is recorded in `<module>/api/*.api`, and the build fails when it changes unnoticed. After
an intended change, run `./gradlew updateKotlinAbi` and commit the new dump.

## How a read travels

```
playsets.findAll(search)
   │
   ▼
SearchSql.pageQuery(search)        generated SELECT  +  WHERE / ORDER BY / seek / LIMIT
   │
   ▼
QueryExecutor.query(sql, params)   prepared statement on PostgreSQL
   │
   ▼
RowContext ──► RowMapper ──► Page<Playset>
```

1. The generated read access passes the search to the entity's `SearchSql`: the fixed `SELECT`,
   plus per searchable field the column a filter or sort uses.
2. `pageQuery` adds the filter, sort, cursor and limit to that `SELECT`, with numbered `$1, $2`
   placeholders.
3. The executor runs it. Each row is read through a `RowContext` (typed access by column name) and
   turned into an entity by the entity's `RowMapper`.
4. Every statement is reported to the registered `QueryExecutionListener`s. That is how the
   [test kit](testing.md) knows what ran.

`findById` is even simpler: it runs the generated `FIND_BY_ID` as it is.

## How a write travels

A write always runs in one transaction. The generated access class runs the entity's statements
top to bottom, in the order the database needs them:

```
owned rows ──► the entity's own row ──► links ──► child rows ──► read the result back
```

Each step is **one round trip for all inputs**: creating 50 playsets costs as many statements as
creating one. After each step, a small helper checks the outcome per input and turns a missing row
into the right exception. See [Writes and relations](writes-and-relations.md).

## Transactions travel with the coroutine

There is no thread-local state. `VertxTransactionalExecutor` puts the running transaction in the
coroutine context, and every persistence call in that coroutine joins it:

```kotlin
unitOfWork.transaction {
    val playset = playsets.create(command)   // same transaction
    notes.create(firstNote(playset))         // same transaction
}
```

See [Transactions](transactions.md).
